## Merge gotchas

When joining `occupancy_panel` (which carries `zone_id`) onto `segments` (which also carries
`zone_id`), drop `zone_id` and `capacity` from the panel **before** the merge to avoid
`zone_id_x` / `zone_id_y` splits. Pattern used in `revenue/forecast.py` and `scenarios/runner.py`:

```python
panel = occupancy_panel.drop(
    columns=[c for c in ("zone_id", "capacity") if c in occupancy_panel.columns]
).merge(seg, on="segment_id", how="inner")
```

## Synthetic baseline calibration

`demand/synthetic_baseline.py` scales each segment's weekly profile between its own off-peak
floor and peak, interpolated by a latent demand intensity. Every anchor is absolute and lives
in `config/demand_baseline.yaml`: covariates are standardised as (log1p(x) - center) / scale
with fixed centers and scales, intensity maps to peak occupancy between fixed
`intensity_low` / `intensity_high`, and the land-use mix is centred on the same fixed centers.
A segment's baseline therefore never depends on which other segments are loaded (audit
finding 24); never reintroduce quantiles, z-scores or means taken over the loaded set.

Centers, scales and intensity bounds come in **anchor sets**, one per reference set of
segments: `synthetic_fixture` (the demo fixture's moments, rounded) and `philadelphia`
(the priced curb of the real `segments.parquet`, generated by
`scripts/derive_baseline_anchors.py` between BEGIN/END markers; `--check` exits 1 when stale,
so rerun it after script 02). `baseline_occupancy` takes the set from
`segments.attrs["segment_source"]["kind"]` via `source_anchor_sets` (fixture ->
`synthetic_fixture`, file or Parking Authority inventory -> `philadelphia`) and raises when
the segments carry no source: `pd.concat` and similar drop `attrs`, so pass `anchor_set=`
then. The weights and the occupancy levels (`peak_target`, `low_demand_peak`, off-peak floor)
are shared and are stated, not measured; the anchors only place a segment relative to its
reference set. `baseline_occupancy` warns when more than `max_clipped_share` of segments sit at
the cap or floor; `panel.attrs["calibration"]` has the set and the shares. Segments the
Parking Authority panel covers should use observed occupancy instead.

## Arnott-Inci zone pricing

`_arnott_zone_prices()` in `scenarios/runner.py` must guard against zones present in the
occupancy panel but absent from `current_prices`. Pattern:

```python
cur_row = current_prices[current_prices["zone_id"] == zone]
if cur_row.empty:
    continue
```

**Peak statistic: the zone's busiest priced hour of capacity-weighted occupancy.** For each
zone, average occupancy across its segments weighted by capacity, hour by hour, over the
zone's priced hours only; take the maximum; price so that hour sits at
`1 - target_vacancy`. Why this statistic and not another:

- Arnott-Inci treat a downtown area as one pool that a cruiser searches block by block, so
  search depends on the zone aggregate, not on any one segment. Hence capacity-weighted
  zone-hours, not segment-hours.
- A zone has one rate across all its priced hours, so the only rate that holds the aggregate
  at or below the target in *every* priced hour is the one that brings the busiest one there.
  Hence the maximum, which is also what "eliminates cruising at the busiest hour" says.
- Unpriced hours are excluded because the rate cannot act on them. Pooling them in (the old
  all-hours q90) let overnight residential occupancy set a downtown rate.
- The panel is a typical-week profile, each hour already an average over weeks, so its
  maximum is not one noisy draw. On real week-by-week data, revisit: a high quantile of
  zone-hours would be more stable.

The choice moves the full-PBD row's sign (audit 2026-10-14, finding 3), so do not swap it
without rerunning scripts 05/06 and updating the prose. Segment-level cruising remains after
the step because blocks busier than the zone average stay over the line; that is a property
of one rate per zone, not a bug. Capacity cancels in the formula, so the code passes
occupancy shares (`capacity=1.0`).

**Floors and ceilings.** The step's rate is the unclipped solution held to the zone's `floor`
and `ceiling` (`seattle_rule.zone_bounds`, the same bounds the Seattle and Chatman-Manville
rules use; the global bounds in `pricing_rules.yaml` for a zone without its own). The zone
floors and ceilings in `zones.yaml` are stated assumptions, with no Parking Authority source in
the repository, and where one binds it sets the rate. Three things keep that visible. (1) The
comparison table carries `n_zones_at_floor` beside `n_zones_at_ceiling`, counted against the
bound in force for the run. (2) A zone whose busiest priced hour is below the target occupancy
has positive *target slack* (target occupancy minus that hour's occupancy): no rate above the
floor reaches the target, and the unclipped solution may be below zero. Each Arnott-Inci run
records per zone, in `diagnostics["zone_pricing"]` (`first_review` against the posted rates,
`last_review` at the state the run ends in): `peak_occ`, `target_occ`, `target_slack`,
`unclipped_price`, the clipped rate, the bounds and `at_floor` / `at_ceiling`. (3) The floor
sensitivity: `run_scenario(..., use_zone_floors=False)` ignores each zone's `floor` (the global
floor still applies; ceilings unchanged) and records `diagnostics["use_zone_floors"]`. Script 05
runs all three scenarios that way at the central elasticity and headline seed and writes the
`no_zone_floors_lo` / `_hi` columns of `scenario_ranges.csv` (rows with `floors == global_only`
in `scenario_runs.csv`). A run with the floors removed is a different run, not a spread of the
same one, so it never enters the seed range.

## Demand form: one law for every price response

`demand/response.py` is the only place demand moves with price. The elasticity priors
(`elasticity_priors.yaml` `scenarios`) are the elasticity *at the zone's posted rate*; the
form (`demand_form`, default `exponential`: q = q_ref exp(e (p - p_ref) / p_ref), elasticity
e p / p_ref) says what happens away from it, so revenue peaks at p_ref / |e| and the Laffer
figure has an interior maximum (audit finding 14). `constant_elasticity` and `linear` are
selectable for sensitivity. **The form and the elasticities (-0.40 central, the -0.2 / -0.7
bracket, the context shifts) are stated assumptions.** Lehner and Peer (2019, TR-A 121: 177-191;
copy in `research/`) support only the sign of the rise of elasticity with price: a significantly
negative coefficient on the hourly price relative to daily GDP per capita (p. 186; EPO -0.10 to
-0.15 in Table 3, EPV -0.03 in all three specifications of Table 5; a cross-study gradient). The
paper estimates no functional form, and its EPV slope against a constant of -0.33 is far shallower
than the exponential's proportional rise: its gradient lies between constant elasticity and the
exponential, and the three forms of the sensitivity bracket it (linear rises faster than
either). Neither -0.40 nor the bracket is a reported estimate; for comparison Table 6
(revealed preference, non-commuting) has 95% intervals EPV -0.45 / -0.18, EPD -0.46 / -0.15 and
EPO -0.72 / -0.54, and the pooled mean EPV of published papers is -0.38 (p. 185). The prior is
labelled the volume elasticity and the model applies it to occupancy, which in the paper's terms
is EPO = EPD + EPV (p. 178). What the form implies is the content to state: elasticity doubles
when the price doubles, and revenue peaks at p_ref / |e| ($10 for Center City Core at -0.4,
$5.71 at -0.7; the sweep's $2 start price peaks at $5.00 and $2.86). The research note's "revenue rises monotonically" for the central case is
the constant-elasticity reading (no peak for |e| < 1), which the default form does not share.

**Per-zone anchoring is an assumption.** Each zone's prior is its elasticity at that zone's own
posted rate, so -0.40 is the elasticity at $1.50 in Fishtown and at $4.00 in Center City Core;
the zones therefore do not share one demand curve. A single exponential law with -0.40 at
$1.50 would give -1.07 at $4.00. The sensitivity is one citywide law: e at a single reference
price p0, each zone's elasticity at its posted rate following from the law
(`citywide_zone_elasticities`; re-anchoring a law at a point on its own curve leaves the curve
unchanged, so the runner's per-zone machinery follows the single law exactly when given those
elasticities, for every form). `run_scenario(..., citywide_reference_price=p0)` runs it;
`diagnostics["demand_law"]` records the anchoring, p0 and every zone's elasticity at its
posted rate. p0 is `runner.citywide_reference_price`, the capacity-weighted mean posted rate of
the priced segments: the central prior is one number for the city, so it sits at the price of
the average priced space (a zone's own rate would make that zone the reference and the others
extrapolations). Script 05 writes it as the `citywide_law_*` columns of `scenario_ranges.csv`
(and `law` / `law_reference_price` in `scenario_runs.csv`), at the central elasticity and
headline seed; it is a different run, never part of the seed range. Every caller passes the reference price: `apply_elasticity(...,
reference_price=<posted rates>)` raises without one; `revenue_curve` and
`_project_occupancy` use the baseline price; `optimal_price_arnott_inci` takes
`reference_price` (the runner passes the status-quo rate, not the rate in force);
the Chatman-Manville sweep anchors at its start price; `cs_change` is the exact integral of
the same law and `cs_change_served` the integral of min(q, capacity), the surplus of the cars
that get a space (see "Welfare objects" below). The hierarchical model still fits log
occupancy on log price: that estimate is
the elasticity at the observed prices, which is what the prior slot means. Do not reintroduce
`(p_new / p_old) ** e` anywhere.

## Priced hours: one mask from `config/zones.yaml`

`phillyparking.pricing.priced_hours` is the only place that decides when a meter is on (per
zone, weekday / Saturday / Sunday windows; a zone absent from `zones.yaml`, such as the
fixture's `other`, is never priced). `apply_elasticity` (response), `annual_revenue` and
`revenue_curve` (revenue), `hourly_search_cost` (the cruising scorer), the Arnott-Inci peak
and the Seattle band statistics all read it. `apply_elasticity` and the search-cost functions
default to `priced_hours_only=True` and need `zone_id` on the panel. The Chatman-Manville
sweep prices only priced hours too, through its own closed-form demand update.

Revenue per zone = zone capacity x the zone's own annual priced hours x capacity-weighted
priced-hour occupancy (x price); for a full weekly panel that equals 52 x the sum over
priced rows of occupancy x capacity x price. Full compliance is assumed.

The Arnott-Inci pricer's target is the scenario's `pricing_policy.target_vacancy`, falling
back to `pricing_rules.yaml` `arnott_inci.target_vacancy` (`diagnostics["target_vacancy"]`).
The cruising scorer has no target in it.

## Seattle rule and convergence

`pricing/seattle_rule.py` follows SDOT's 2024 rule: one statistic, the band's average
capacity-weighted zone occupancy over the zone's priced hours, per `time_of_day_bands`
(`scenarios.yaml`); above `occ_high` +$0.50, below `occ_low` -$0.50, inside the band hold.
Prices are per zone x band; `priced_hours.hourly_prices` expands them to hours.

The runner reviews annually until no rate moves by more than $0.001 (a fixed point) or prices
repeat with period 2; `rolls_forward_years` is a cap, not a horizon. A two-cycle is reported
as both phases (`diagnostics["phases"]`, and `<name>_phase_a` / `_phase_b` columns in the
comparison table), never as one year's state. With the dead band, a cycle can still occur where
one $0.50 step moves demand across the whole band: under the exponential demand form a step
multiplies demand by exp(|e| 0.5 / p_ref), which exceeds 0.85/0.70 only when |e| / p_ref is
above about 0.39 (Fishtown at the pessimistic elasticity; no zone at the central one).

## Chatman-Manville sweep: one rule module, paired runs, scored on welfare

`pricing/targeting_rules.py` is the only implementation of the sweep's rules: the statistic
(peak = q95 of block-hours, or their mean) x the instrument (one rate per zone, or per zone and
time-of-day band) gives `peak_zone`, `mean_zone`, `peak_band`, `mean_band`; `seattle_rule` is the
project's own rule; `min_vacancy_peak` / `avg_occupancy` are the original 168-hour rules, kept for
`ordering_violations`. All step +-$0.50 against the same 0.70 / 0.85 band (`chatman_manville:` in
`pricing_rules.yaml`, kept equal to Seattle's by a test), honour `zones.yaml` floors and ceilings,
read only priced hours, and take the rate in force from priced rows (meter-off rows may carry a
stale price). `scenarios/cm_sweep.py` runs them and builds the summaries.

**Why welfare, and what the breakeven is.** Search cost falls in price and revenue rises in
it (up to the revenue peak), so on either alone the higher statistic wins by construction. The
sweep therefore scores each priced block-hour on `welfare/targeting_welfare.py`: consumer
surplus change + revenue - search cost, all three on the cars that park (see "Welfare
objects"). The search cost is the project's one cruising model (`welfare/search_cost.py`); its
level is a stated assumption, and welfare is linear in it, so every row carries
`search_cost_per_cruising_minute` and `paired_table` reports each comparison's breakeven:
`breakeven_cruising_minutes`, the level at which the two rules tie, in the level's own units
(the mean cruising time of the drivers who cruise when every block is full, the units of the
cited studies; the headline), and `breakeven_reference_minutes`, the same level quoted as
search per arrival at the 95% reference block-hour (c* x `reference_minutes_per_cruising_minute`,
which depends on the cap: 0.60 at 0.95, 0.14 at 0.99, 0.015 at 0.999, so that column is not
comparable across caps).
For a same-instrument pair (`mean_zone` vs `peak_zone`, `mean_band` vs `peak_band`) the SIGN
of the breakeven is a property of the design, not a finding: a mean is never above a q95 of
the same block-hours, so the mean rule prices at or below the peak rule, total surplus
(surplus + revenue) is higher at the lower price and search cost higher at the higher
occupancy, in every replication; `ordering_violations` tests it. The
sweep's content for such pairs is the SIZE of the breakeven against the cruising times the
config cites (`search_cost.cited_cruising_minutes`: Shoup 2006, 3.5-14 minutes, per cruiser,
the same units as the breakeven; `cm_breakeven_*.png` shade that range). The sign is not an identity across instruments or for
`seattle_rule`.

**What `ordering_violations` checks.** Two things per replication-year: the comparator's search
cost is not below the reference's, and its total surplus (`cs_change + revenue`) is not below the
reference's. Not revenue alone (the mean rule earns less below the revenue peak and more above
it, so revenue has no sign there) and not the price paths (the premise that the mean rule prices
at or below the peak rule is the argument for the check, not something it tests). Total surplus
falls in price under every form, including above the revenue peak, because d(CS + p q)/dp =
p q'(p) <= 0 (and 0 on a rationed block); so an empty frame is the ordering holding on the
sweep's draws, a property of mean <= q95 and a monotone demand law.

**Axes** (`chatman_manville_sweep:` in `scenarios.yaml`): elasticity; `start_occupancy` m
(each zone's priced-hour mean at the start price, set by scaling its latent demand; the band
edges are avoided); `block_dispersion` tau (a lognormal block multiplier, u fixed per block and
replication); `observation_noise` sigma (what the rule reviews is true occupancy + sigma z,
redrawn yearly; welfare is scored on the truth, so noise biases a peak statistic upward);
`occupancy_cap` (the search cost's cap: the rules never see it, so each rule's price path is
run once and scored once per cap, and the rows of one path differ across caps only in
`search_cost`, `search_cost_per_cruising_minute` and `welfare_change`). Demand is latent
and unclipped: d = d0 x `demand_level(p)` in closed form (path independent, the same law as
`apply_elasticity`); occupancy is min(d, 1). u and z are shared by every rule and cell in a
replication (paired). The fixture is `fixture` (n=120, seed 42) with the never-priced "other"
segments dropped; the baseline uses the `synthetic_fixture` anchor set.

Report per cell, never pooled: `cell_table` (median and range), `paired_table` (each configured
`comparisons` pair per replication: welfare, surplus, revenue and search-cost differences, the
two breakeven columns, search-cost and revenue ratios), `window_dependence` (across the cells
of the other four axes, one row per comparison and cap, so the cruising-minute breakeven's stability
across caps is visible). The year charts are drawn at the config's default cap. The sweep is a
mechanism study on a fixture: the within-day shape is the baseline's, the search-cost
parameters are unmeasured, and the fixture's zones are nothing like Philadelphia's. Provenance
(git state captured when the run starts) is in `outputs/tables/cm_sweep.meta.json`. Regenerate
with `scripts/07_export_report_assets.py --rebuild-cm-sweep` (over an hour at 100 replications).

**Demand-form sensitivity and where the cells sit.** The headline sweep is under the
exponential form. `scripts/07_export_report_assets.py --rebuild-cm-form-sensitivity` (run alone,
about 15 minutes) reruns the sweep at the same grid and draws under the exponential, linear and
constant-elasticity forms at 20 replications each (`FORM_SENSITIVITY_REPLICATIONS`; replication r
of a short run is replication r of a long one) and writes, to `outputs/tables/`:
`cm_sweep_form_sensitivity.csv` (per form, comparison and cap, in the last year: the median and
range over cells of the per-cell median breakeven and welfare difference, `n_cells`,
`cells_welfare_better`; the exponential rows are the headline form at 20 replications),
`cm_sweep_form_beyond_peak.csv` (per form, elasticity and rule: that form's revenue-maximising
price, the share of rule-years whose mean price is above it, over all years and in the last year)
and `cm_sweep_form_sensitivity.meta.json` (provenance; tied to the config like the sweep's).
The forms agree near the start price and disagree where the rules go: the peak rules settle
at roughly two to two and a half times the start price, where the exponential elasticity is
that multiple of e, and at e = -0.7 the
exponential revenue peak ($2.86) is below that price, so most peak-rule rule-years there sit
beyond the point where the law's own revenue falls (the beyond-peak file has the share; the
mean and Seattle rules stay below the peak). The cells at -0.7 are statements about a law
extrapolated past its revenue peak; the -0.2 and -0.4 cells sit mostly below it. Constant
elasticity has no peak at |e| < 1 and the linear form has a choke price, so a statement
about the sweep is a statement about its form until the form-sensitivity rows agree.

## Welfare objects: one cruising model, one population

`welfare/search_cost.py` is the project's only cruising cost, used by the scenario runner's
cruising row (`ScenarioResults.search_cost`, `search_cost.parquet`, `search_cost_total` in the
comparison table) and by the sweep's scorer. An arriving driver checks a block of
K = `search_unit_spaces` spaces at the occupancy o of the segment they arrive at; it is full
with probability o^K, and the driver passes p/(1-p) full blocks; cost per segment-hour =
served arrivals (occupancy x capacity / `mean_duration_hr`) x minutes x value of time. It is
convex in occupancy and has no occupancy target in it.

**The search unit is the block, not the segment.** A segment is a piece of centerline cut at
intersections, attribute breaks and by the builder at about 80 m (`spatial/segments.py`); its
capacity counts one curb side, length / 7 m x 0.85, so it is set by where the data break the
street. Passing a block costs the same minutes wherever it is, so a segment-sized unit would
charge a short segment far more per arrival at the same occupancy (85 minutes for one space at
the 0.99 cap against 8.1 for ten). With the fixed unit, search minutes per arrival are a
function of occupancy alone (`expected_search_minutes` takes no capacity), capacity enters
only through arrivals, and the cost is additive over any cut of the curb
(`test_cost_is_additive_over_any_cut_of_the_curb`); keep it that way. Alternatives weighed in
the PR that introduced the unit: pooling segments into blocks by centerline topology leaves
short pieces short (priced curb is fragmented and the centerline breaks at alleys); a
per-segment unit whose pass time scales with its spaces agrees with the fixed unit near the cap
(K o^K / (1 - o^K) hardly depends on K there) but still depends on the cut at moderate
occupancy. The unit's size matters only away from the cap: it barely moves the reform
scenarios' search cost, which sits at the cap, but moves the status quo's several-fold, because
no status-quo priced block-hour is near the cap, so read that cell as unpinned by this model.

**Level units.** `cruising_minutes_at_full_block` (`search_cost:` in `pricing_rules.yaml`) is
the mean search of the drivers who cruise when every block is full, the units of
`cited_cruising_minutes` (Shoup's range, 3.5-14, mean 8.1: the average cruising time of those
who cruise); the level is set at that mean. A cruiser passes 1/(1 - cap^K) full blocks, so the
per-block constant is level x (1 - cap^K); an arrival at a full block cruises with probability
cap^K, so its expected search (`SearchCostConfig.minutes_at_full_block`) is cap^K x level: 7.3
at cap 0.99, 4.9 at 0.95, 8.0 at 0.999. The `occupancy_cap` decides how much more a full block
costs than a 95% one (6.3x at 0.99 on 10 spaces, 1x at 0.95, 67x at 0.999); it must be below 1.
No Philadelphia measurement of any of these exists. There is no second cruising model: the old
linear proxy (excess over the target x 5 minutes x $20) had the pricing target built into it
and scored zero below it, so it could only restate the band; do not reintroduce it, and do not
put a cruising constant in a function default.

Every welfare term counts the same population, the cars that park. Consumer surplus is
`demand.response.cs_change_served`, the exact integral of min(q(x), capacity) (the block is
rationed to the parkers who value it most); revenue is served cars x price; the search cost
charges served arrivals. A block-hour whose latent demand exceeds its capacity therefore loses
exactly capacity x the rise in surplus when its price rises and stays full, and the cars it
turns away carry neither surplus nor search cost. Both the runner (`_annual_cs_change`) and
the sweep use the served integral; `cs_change` (latent) remains for the integral's own tests.

The scenario table prints parkers' surplus + meter revenue as one row (both as changes from
the status quo: `surplus_plus_revenue_change` in `compare.py`, a valid partial object) and the
search cost labelled with the level it is scored at; it never prints a net of the two, and the
app follows the same layout. The level is a stated assumption, so the sweep's breakevens, not a
net at the config level, are what the project reports.

`hourly_search_cost` merges `segments[["segment_id", "capacity", "zone_id"]]` onto the panel
after dropping the panel's own `capacity` and `zone_id`; keep that drop, or a panel that
already carries them (the sweep's does) gets `capacity_x` / `capacity_y`.

## Gini coefficient

`welfare/incidence.py` computes Gini via Lorenz curve. The curve **must** prepend (0, 0):

```python
lorenz = np.concatenate([[0.0], np.cumsum(sorted_weights) / total_wv])
```

Without the prepended zero, equal-income groups return 0.0625 instead of 0.0.

## Data acquisition: public layers

Every loader goes through `io/raw_cache.load_layer`. A real fetch is cached under the layer's
own filename with a sidecar `<file>.provenance.json` (layer, kind real/synthetic, source, URL,
UTC fetch time); failures are retried, then raise `LayerFetchError`. A synthetic stand-in is
written only with `allow_synthetic=True` / `PHILLYPARKING_ALLOW_SYNTHETIC=1` (scripts:
`--allow-synthetic`), and only as `<stem>.synthetic<suffix>`. A file with no marker is refused
(`UnknownProvenanceError`): the pre-marker loaders saved synthetic layers under real names, so
the old `data/raw/` cache must be refetched with `scripts/01_download_public_data.py --refresh`.
Script 01 exits 1 if any layer is not real; script 02 records every layer's marker in
`data/processed/segments.meta.json` and never skips a join.

Sources (checked live 2026-10-15): Street Centerline (ArcGIS FeatureServer, paged), RPP blocks
(Carto `residential_parking_permit_blocks`, POINTS with `district_number`), neighborhoods
(odp-data-storage GeoJSON), zoning (Carto `zoning_basedistricts`), ACS 5-year block groups
(Census Data API, needs `CENSUS_API_KEY`; geometry and `ALAND` from `cb_<year>_42_bg_500k`;
cenpy cannot request these vintages), LODES8 WAC/RAC plus `pa_xwalk.csv.gz` block internal
points, OSM via osmnx, SEPTA GTFS (one archive holding `google_bus.zip` and `google_rail.zip`,
read as two feeds). There is no public meter inventory: `fetch_meters` raises; meters come from
the Parking Authority release. Census API errors are re-raised without the request URL, which
carries the key.

**Which segments a zone prices** (`zones.yaml` `priced_curb`, `spatial/segments.py`).
`build_segments` drops City centerline classes with no curb (`no_curb_classes`: expressways,
ramps, driveways, walkways; codes from the centerline metadata) and keeps `street_class`.
`assign_priced_curb` sets `zone_box` (the box the segment lies in) and makes `zone_id` that box
only for priced curb, else `other`. With `--meters` priced curb is `has_meter`; without an
inventory it is a stand-in: class 2-5 and `commercial_frontage_share >= min_commercial_share`
(`join_zoning`: share of the zoned land within 25 m, flat ends, in the Commercial/Commercial
Mixed-Use group; zoning stops at the property line, so the buffer must reach across half the
street). The rule is recorded as `priced_curb_rule` in `segments.meta.json`. Changing the rule
or the inventory changes the `philadelphia` anchors: rerun `derive_baseline_anchors.py`.

Join columns are defined in the `spatial/join.py` docstring. `jobs_within_200m` counts LODES
jobs of the blocks whose internal point lies in the buffer; ACS attributes are buffer-share
weighted and renormalised over the covered part. Zone boxes overlap; `zones.zone_for_point`
gives a point to the smallest box containing it. The segment builder keys ids on `seg_id`, or
`osmid|u|v|key`, splits MultiLineStrings, drops reverse twins of two-way OSM edges, and counts
everything in `segments.attrs["build_report"]`.

## Parking Authority data: ingestion and identification

The RTKL packet is at `docs/rtkl/` (`docs/rtkl/README.md`; PPA's RTKL email
`OpenRecordsOfficer@philapark.org`). `ingest/ppa.py` (script `03b_ingest_ppa.py`) reads
sessions, the meter inventory and the rate schedule through `config/ppa_ingest.yaml`, a
column mapping: when the real export arrives, edit the mapping, not the code. It writes a
panel by segment x calendar period x hour of week with `price_usd_per_hr` = the posted rate
in that period; periods are cut at the schedule's effective dates. Occupancy = paid minutes /
(spaces x 60 x calendar dates of that weekday in the period) / (1 - `unpaid_share[zone]`);
`unpaid_use.unpaid_share` must be stated in the config (0.0 = paid occupancy, a lower bound).
Every ambiguity raises `PPAIngestError` (see the module docstring). `runner_inputs` picks one
period for the runner and refuses a period whose posted rates differ from `zones.yaml`.
`--stub` ingests `ppa_stub.make_known_answer_export` into `data/processed/ppa_stub/`, never into
`data/processed/ppa/`.

`elasticity/identification.check_identification` rank-tests the design (zone intercepts,
zone x log price, hour-of-week and period effects) and raises `IdentificationError` when no
zone's elasticity is identified; `fit_elasticity_model` calls it before importing PyMC and
adds `delta[period]` when the panel has a `period` column. Script 04 fits only priced hours of
an ingested panel and exits 1 when nothing is identified (`--allow-prior-only` writes the prior
labelled `prior_only`). One period (one price per zone) identifies nothing; two zones whose
rates both changed, with no unchanged zone, are not identified once the period term is in.

## Allocation, consumer surplus, ranges

`revenue/allocation.py` follows 75 Pa.C.S. § 6109(g) (Act 84 of 2012; citation, text and
retrieval date in `config/allocation.yaml`): General Fund first, up to the $35M minimum, then
the PBD share from what is left, then the School District. The statute has no PBD payee, and
the City's amount is not reduced by expenses, so a PBD can only be paid from the School
District's excess; the unpaid part of its share is `pbd_unfunded_usd`. At the fixture's scale
(a few $M against a $35M minimum) the General Fund takes everything, so PBD and School District
rows are $0 and the PBD's claim shows as unfunded: read the allocation as an order of payment,
not a forecast. The model uses gross meter revenue and no escalator, the statute net revenue
citywide and an escalated minimum.

`cs_change_total` is annual dollars: over every priced block-hour, the integral of served
demand min(q, capacity) from the posted rate to the scenario's hourly price
(`runner._annual_cs_change`, using `demand.response.cs_change_served` with the baseline
panel's demand as q_ref), times 52; no search-time term. A zone with priced block-hours and no
price raises; no default price is invented. `welfare/consumer_surplus.py` (nested-logit
logsums) is no longer used by the pipeline.

Script 05 also writes `scenario_ranges.csv` and `scenario_runs.csv` (copied to `outputs/tables/`
by 06): the other two named elasticities at the headline seed, and the central elasticity at
fixture seeds 0..n-1 (`--n-seeds`, default 20). On segments that are not the synthetic fixture
nothing depends on the seed (the panel is deterministic in the covariates and the surplus term
is an integral), so the seed loop is skipped and only the elasticity range is written.
`pessimistic` (-0.7) gives the highest revenue because both reforms are net price cuts. A Seattle
two-cycle pools both phases in each range cell. The ranges carry `search_cost_total`,
`cs_change_total`, `surplus_plus_revenue_change` and the at-bound counts like any other row.
`incidence_by_decile.png`
is a constant placeholder, stamped as such in the figure; `Report.tex` still includes it.

Script 06 draws the Center City Core Laffer curve twice at -0.4: `laffer_curve_ccc.png` under
the configured form, and `laffer_curve_ccc_forms.png` with all three forms on the same axes
(`viz.charts.laffer_curve_forms`; `revenue_curve(..., form=)`), so the existence and location of
the peak are visibly the form's.

## Tests

Run with `C:/Users/druss/miniconda3/python.exe -m pytest tests/` from the project root.
The full suite takes about 10 minutes, almost all of it in one test:
`test_hierarchical_bayes.py::test_fit_recovers_true_elasticity`. PyTensor finds no C compiler
on this machine ("g++ not detected"), so PyMC samples in pure Python. Every other test,
including the e2e test, runs in seconds. For rapid iteration, skip the PyMC test with
`-k "not hierarchical_bayes"`.

**Artifacts are tied to the config.** `scenarios/provenance.config_hashes()` hashes every
`config/*.yaml` (CRLF read as LF, so a Windows and a Linux checkout agree), and the scenario
`meta.json` files and `cm_sweep.meta.json` record it. `tests/test_config_ties.py` compares each
recorded hash set with the tree's and fails naming the script to rerun (05, 06, 07 for the
scenarios; `07 --rebuild-cm-sweep` for the sweep). Any edit to a config file, a comment
included, therefore stales the tracked sweep until it is rebuilt. The same file pins
direction of change instead of values: raising `peak_target` or `low_demand_peak` raises baseline
revenue and each zone's unclipped Arnott-Inci price, and raising `search_cost.cruising_minutes_at_full_block`
scales every scenario's search cost by the same factor and leaves revenue alone.
